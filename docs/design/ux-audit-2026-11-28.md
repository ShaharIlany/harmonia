# Harmonia UX audit, 2026-11-28

A pass through Harmonia as a power user who manages the six teammates every day: routing work, approving
permissions and tools, watching jobs, tuning teammates and checking cost. Each finding says what's wrong, how to
reproduce it, what should happen, why, and where the idea comes from.

Audited build: `main` at `970af3c` (after the shadcn-neutral restyle, `e0b9515`), desktop at 1280×820 and phone
width (375×812), dark and light. The installed app (port 4747) was only looked at, never changed.

## How to reproduce (isolated stub, no real Claude runs)

Never use the real data folder or the real `~/.claude` (see `CLAUDE.md`). From a checkout or worktree:

```bash
S=$(mktemp -d)                                   # any temp folder
python3 docs/screenshots/demo-data.py "$S/data"  # demo channels: #dark-mode, #csv-export, …, user "Alex"
mkdir -p "$S/claude/agents" "$S/cwd" && cp agents/*.md "$S/claude/agents/"
HARMONIA_USER=Alex HARMONIA_STUB=1 PORT=4751 HARMONIA_DATA="$S/data" CLAUDE_CONFIG_DIR="$S/claude" HARMONIA_CWD="$S/cwd" bun server.ts
```

Or add the same env as a `.claude/launch.json` configuration and use `preview_start`. With `CLAUDE_CONFIG_DIR`
pointed at a temp folder, the Setup check says the CLI is signed out: that's expected here, and it's also how F4
shows up.

Stub triggers used below (last line of a message): a message containing the word `job` starts a stub job;
`stub-permission` makes that job ask for permission; `need a tool` makes the teammate request a tool.

## F1 · Critical · Pending permission and tool cards render as already decided

**1. What's wrong.** Every *pending* approval card is drawn as if it had been decided:

- A job's permission request shows `✓ undefined · Bash: Bash: bun test`, with a green tick and no Allow once /
  Always / Deny buttons.
- A teammate's tool request shows `✕ Denied`, with no Approve / Deny buttons.

The same broken cards appear in the **Waiting on you** panel, which still counts them (the header badge says 3),
so the user is told something waits on them and given no way to act. A job that needs permission can't be resumed
from the UI, and a tool request can't be approved: both core loops of managing the team are dead.

Cause: `cardHtml` in `public/app.js` (around lines 306–331). The restyle (`e0b9515`) changed the decided check to
`if (p.status)` / `if (r.status)`, but a pending card's status is the string `"pending"` (`team.ts` lines 974 and
1149), which is truthy. Before the restyle the code looked the label up by status, so `"pending"` fell through to the
buttons. Two smaller defects in the same line:
- the permission label map has no `"pending"` key, hence `undefined`;
- `p.summary` already starts with the tool name (`describeTool` in `runner.ts` returns `Bash: bun test`), so
  `${p.tool}: ${p.summary}` prints `Bash: Bash: bun test`.

**2. How to reproduce.**
1. Start the stub (top of this file) and open `#dark-mode`. Murphy's 09:46 tool request already shows `Denied`, though
   its stored status is `"pending"`.
2. Send `@Elliot start a job stub-permission`. Elliot's job card says *Needs permission*; under it the permission card
   reads `✓ undefined · Bash: Bash: bun test`.
3. Send `@Murphy I think you need a tool`. The new tool card reads `✕ Denied` at once.
4. Open **Waiting on you**: the badge says 3, and all three items show the broken decided state with no buttons.

**3. Expected.**
- Pending permission: the full card, with *Allow once*, *Always in this channel* and *Deny*.
- Pending tool request: the full card, with the reason, the tool chips, *Approve* and *Deny*.
- Decided permission: `Allowed once · Bash: bun test` (tool shown once). Decided tool request: `Approved: Murphy has
  it from now on` or `Denied: clickup_delete_task`, naming what was denied.
- Waiting on you shows the same working buttons, and deciding a card there or in the chat clears it from both places.
- Test: a unit or DOM test that renders `cardHtml` for `status: "pending"` and asserts the buttons are there, so
  the next restyle can't break it silently.

Suggested fix: treat only the final states as decided (`p.status && p.status !== "pending"`, same for `r`), and
build the summary from `p.summary` alone.

**4. Why.** Approval is the safety valve of the whole product: the docs say jobs ask before risky actions and that you
approve permissions and new tools from cards in the chat. A card that looks approved when it isn't is worse than a
missing card, because it tells the user nothing is needed. A denied-looking card also hides what was requested.

**5. Inspiration.** GitHub's "Review required" and Slack's interactive approval messages (workflow approvals, the
Jira/PagerDuty apps): an open request always shows its actions, and a decided one names who decided what. Claude
Code's own permission prompt shows the exact command once, never repeated.

## F2 · High · The channel name is the first thing to disappear from the header

**1. What's wrong.** The header (`.hdr` in `public/style.css` ~261–284, markup `index.html` ~103) gives the channel
name no priority. When the right panel (Sessions or Waiting on you) is open at 1280 px:

- `#dark-mode` shrinks to `# d…`, `#csv-export` to `# c.`, and with Waiting on you open the name is gone completely,
  leaving `# APP-151`.
- The status pill is cut (`In progre…`, `Waiting for respon…`) and the participant avatar stack is drawn **on top of**
  the status pill text.
- At phone width (375 px) the name is `# c` while the task chip and the Session/Weekly meters keep their full width.

The same happens on real data, where a channel with an ordinary name is cut to its first few letters.

**2. How to reproduce.** Stub, 1280×820. Open `#csv-export`, click **Sessions**: the name shows as `c.`. Click
**Waiting on you**: the name is gone and the avatar overlaps the `Waiting for response` pill. Resize to 375×812:
`# c`.

**3. Expected.** The channel name is the last thing to give way, after everything else:
1. Name: never below about 8 characters plus an ellipsis; full name in a `title` tooltip.
2. Then drop, in order: the folder line's path (keep the icon), the participant stack, the status pill's text (keep
   its coloured dot), the task chip's text (keep `APP-142` only when there's room), the "Waiting on you" label (keep
   icon + count) and the "Sessions" label (keep the icon).
3. Nothing overlaps: the avatar stack hides instead of sliding under the pill.
Use flex priorities (`flex-shrink: 0` and a `min-width` on the name; `flex-shrink` on the others) or a container
query on the header, and test at 1280 with a panel open, at 1024, and at 375.

**4. Why.** The name is the one thing that tells the user where they are, and they act on it (typing a message,
approving a card). Losing it while a decorative avatar stack and a long status label stay is the wrong trade-off.
Overlapping text is a visible defect.

**5. Inspiration.** Slack's channel header keeps the channel name and truncates the topic first; Linear's issue header
collapses labels to icons before touching the title; WhatsApp's chat header keeps the name and drops the
"last seen" line.

## F3 · High · Leaving a teammate's settings throws away unsaved edits without asking

**1. What's wrong.** On a teammate's page (`public/agent-page.js`), editing a field enables **Save changes** and shows
"N unsaved changes" in the sticky bar, but clicking a channel, another teammate, the usage link or the back button
leaves the page and drops the edits silently. Coming back shows the old values. The instructions editor is long, so
this loses real work.

**2. How to reproduce.** Stub. Right-click **Elliot** in the sidebar → *Settings and memory*. Change **Role** from
`Code` to `Code writer` (Save changes turns on). Click `#csv-export` in the sidebar. Open Elliot's settings again:
Role is `Code`, and nothing warned you.

**3. Expected.** Leaving the page with unsaved changes asks: *"Elliot has 1 unsaved change. Save / Discard / Keep
editing"*. The same guard for closing the window or reloading (`beforeunload`), for switching to another teammate's
page, and for the Setup page's settings form. Optionally keep a draft per teammate so a slip doesn't cost anything.

**4. Why.** The page already tracks the diff (`save-status`, `save-bar.dirty` around `agent-page.js:243`), so the
guard is cheap. Instructions are the teammate's behaviour: losing a careful edit is costly and invisible.

**5. Inspiration.** macOS document apps (the "Do you want to save the changes…" sheet), VS Code's unsaved-tab prompt,
GitHub's "Leave site? Changes you made may not be saved" on an edited issue body.

## F4 · High · Signed out, the footer clips "Quick login" and hides the Slack entry completely

**1. What's wrong.** The sidebar footer's status line (`.me-status`, `style.css` ~217–229) puts the CLI status and the
Slack status in one `nowrap; overflow: hidden` row. `#cli` is `flex: none`, so when it says
`● CLI signed out · Quick login` it takes the whole width: **Quick login** is cut to `Quick lo`, and the
`#slack-status` button (`Slack off`) gets **0 px** width. It's in the DOM but can't be seen or clicked, and the
Slack page has no other entry point.

On real data the same slot shows `Slack on` or `CLI signed in` at different moments, so the place you click to
reach Slack isn't stable either.

**2. How to reproduce.** Stub with `CLAUDE_CONFIG_DIR` set to a temp folder (the CLI then reads as signed out). Look
at the footer under the user's name: `CLI signed out · Quick lo`. In the console:
`document.getElementById('slack-status').getBoundingClientRect().width` returns `0`.

**3. Expected.** Each status gets its own place and stays readable at the 212 px sidebar width:
- A signed-out CLI is a problem, so it gets a clear row or banner of its own: `⚠ Claude Code signed out ·
  [Quick login]`, with the button whole.
- Slack always has its own entry (a row in the footer, or an item in the settings ⚙ menu next to Setup check and
  Usage) showing `Slack: on / off / reconnecting`.
- No status is ever squeezed to zero; if room runs out, wrap to two lines.

**4. Why.** Signing in is the first thing a new user needs, and the fix button is the part that gets cut. Hiding the
only way into Slack setup makes a whole feature undiscoverable.

**5. Inspiration.** Slack's and Discord's bottom-left user area (status on its own line, settings in a menu); VS Code's
status bar, where each item is a separate fixed control; macOS menu bar extras, which never overlap.

## F5 · Medium · The hover toolbar covers the message text and the job status badge

**1. What's wrong.** `.hover-actions` (React / Reply / Feedback / ⋯) is positioned at `top: -14px` inside the bubble
(`style.css` ~323). It's about 30 px tall, so it sits on the bubble's first line. On a one-line bubble it hides the
middle of the sentence (`(stub) Got it, emily here. I read: … why the build is slow?` loses `the build is`). On a job
card it covers the **Needs permission** / **Done** badge, the most important word on the card. On phones a
permanent `⋯` sits on every bubble's top edge.

**2. How to reproduce.** Stub, `#audit-…` or `#dark-mode`. Hover a teammate's one-line message: the toolbar covers
the text. Hover Elliot's job card `j2`: the toolbar covers *Needs permission*.

**3. Expected.** The toolbar never covers content: put it in the gutter beside the bubble (the outside edge,
vertically on the first line), or above the bubble in the row's own padding with room reserved, the way the name
line already reserves space. Keep it keyboard-reachable (`:focus-within`). On touch, a long-press menu instead of a
permanent `⋯`.

**4. Why.** Hover controls exist to act on what you're reading; hiding the text or the status you're about to act on
defeats them. The job badge is the thing you check before deciding.

**5. Inspiration.** Slack's message actions float in the message row's top-right over empty space, not over text;
iMessage and WhatsApp put the reaction trigger outside the bubble.

## F6 · Medium · The side panel ignores Esc, and × on "Waiting on you" opens Sessions

**1. What's wrong.**
- With Sessions or Waiting on you open, **Esc** does nothing (the only Esc handlers are for the search box, the
  mention pop-up and the reply bar, `app.js` 229, 1561, 1563).
- With Sessions open, clicking **Waiting on you** swaps panels; clicking **×** on Waiting on you then brings
  Sessions back instead of closing. The × reads as "close" but acts as "back".

**2. How to reproduce.** Stub. Click **Sessions**, then **Waiting on you**. Press Esc: nothing. Click × on Waiting on
you: Sessions appears.

**3. Expected.** Esc closes the top-most layer (menu → dialog → side panel), when focus isn't in a field that uses
Esc itself. × closes the panel. If going back to the previous panel is wanted, show a `←` back button for it, and
keep × for closing everything.

**4. Why.** Esc to dismiss is a platform convention every Mac user expects; an × that opens something else breaks
the user's model of the layout.

**5. Inspiration.** macOS HIG (Esc cancels or dismisses), Slack's thread and profile side panels (Esc and × both
close), the WAI-ARIA dialog pattern.

## F7 · Medium · Job cards say "Finished" when the job didn't finish

**1. What's wrong.** `jobCard()` (`app.js` ~570) prints `Finished <time>` for any job with `endedAt`, whatever its
status. A job waiting for permission reads **Needs permission … Finished 01:28**, which contradicts itself; failed
and stopped jobs say "Finished" too.

**2. How to reproduce.** Stub: send `@Elliot start a job stub-permission`. The card says *Needs permission* in the
header and *Finished 01:28* in the footer.

**3. Expected.** The footer follows the status: `Done 09:41`, `Paused 01:28 · waiting for your OK` (with a link that
scrolls to the permission card), `Failed 01:28`, `Stopped by you 01:28`. Use the same words in the Sessions panel's
job list.

**4. Why.** The footer is the line people scan to see whether a job needs them. "Finished" on a job that is waiting
for them makes them skip it.

**5. Inspiration.** GitHub Actions run status ("Waiting for approval", "Cancelled", "Failed" with a time each);
Buildkite's "Blocked" state, which says what unblocks it.

## F8 · Medium · ⌘K finds only channels, and the DM list ignores the query

**1. What's wrong.** ⌘K focuses the sidebar search, which filters channel rows by name or task only. Typing a
teammate's name (`elliot`) shows *No channel matches "elliot".* while the **Direct messages** list below stays
unfiltered, all six names. There's no way to search message text, job titles or reports.

**2. How to reproduce.** Stub. Press ⌘K, type `elliot`: "No channel matches", and the DM list still shows Dali, Leo,
Elliot, Sherlock, Murphy and Emily.

**3. Expected.**
- The query filters DMs too (Elliot's DM row is a match), and Enter opens the first match.
- Better: ⌘K opens a quick switcher listing channels, DMs, teammates' settings pages, and recent jobs (`j2 Stub job ·
  #dark-mode`), with arrow keys and Enter.
- Later: message search across channels (the messages are local JSON, so a simple substring search is cheap).

**4. Why.** A power user jumps between a dozen channels and six teammates all day; the keyboard is the fastest path,
and "No match" next to a visible match looks broken.

**5. Inspiration.** Slack's ⌘K quick switcher (channels, people and DMs together), Linear's ⌘K command menu, VS
Code's ⌘P.

## F9 · Medium · A channel that runs everything without asking shows no sign of it

**1. What's wrong.** A channel's Permissions choice (run everything without asking / edit files freely / ask before
edits and commands) lives only in the channel's right-click menu. The header, the composer and the job cards say
nothing, so you can't tell at a glance which channels let jobs run unattended. The global default (`permissionMode`
in `settings.json`) isn't on the Settings page at all (`docs/settings.md` line 31 says so).

**2. How to reproduce.** Stub. Open `#dark-mode` and look at the header and composer: no permission indicator.
Right-click the channel: *Run everything without asking* is ticked. Open Setup check → Settings: no default
permission field.

**3. Expected.**
- A small, quiet indicator in the header's second line next to the folder, e.g. `⏵⏵ Runs without asking` (or
  `Asks before commands`), which opens the same choice on click.
- The job card shows the mode it ran under when that wasn't the default.
- Settings page: a "Default for new channels" choice for `permissionMode` (Bypass / Edits only / Ask), with the
  current effective default named. Update `docs/settings.md` and drop its "not on the settings page" line.

**4. Why.** It's the riskiest setting in the app; it decides whether a job can run any command in that folder
without you. Settings that change what an agent may do should be visible where the agent works.

**5. Inspiration.** Claude Code's own status line (`⏵⏵ bypass permissions on`, shift+tab to cycle); GitHub's
"Protected branch" badge on the branch picker; browsers' site-permission icon in the address bar.

## F10 · Medium · Settings says "Restart Harmonia" but offers no way to; sign-in fix is plain text

**1. What's wrong.**
- On Setup check → Settings, most fields say *Needs a restart*, and after saving the page says **Restart Harmonia**
  for *X* to take effect (`setup-page.js` ~80–88), but there's no button. The user has to quit and reopen the app,
  and nothing says whether that's safe while teammates or jobs are working.
- The *Claude Code is signed in* check says "To fix: Open a terminal and run: claude auth login", while the sidebar
  has a working **Quick login** button for exactly this.

**2. How to reproduce.** Stub. Open Setup check (⚙ at the bottom of the sidebar). Change *ClickUp task prefix*,
press Save: the toast says "Saved. Some changes need a restart." and the card shows *Restart Harmonia for …*, with no
control. Scroll up: the sign-in item is text only.

**3. Expected.**
- A **Restart now** button next to that line. It restarts at once when nobody is working; otherwise it's disabled
  with "Restarts when Leo and 1 job are done", or offers "Restart when idle" (the update path already waits for
  idle). Never restart while teammates or jobs work.
- The sign-in check has a **Quick login** button (the same action as the sidebar's `data-cli-login`), then
  re-checks.

**4. Why.** Telling the user what to do instead of doing it is friction, and an unguarded restart would kill running
jobs. The app already has both actions.

**5. Inspiration.** VS Code's "Reload window to apply" notification with a Reload button; macOS System Settings
("Restart…" inside the pane that needs it); Docker Desktop's "Apply & restart".

## F11 · Medium · The routing note's tooltip blames Mozart for plain replies, and hides real Mozart failures

> **Correction (after review):** part of this finding came from the demo data, not the app. The server writes no routing note for a reply or an @mention (the `reply to Leo's message` note is an old line in `docs/screenshots/demo-data.py`), and a real Mozart failure already reads `Mozart failed: …`. The stub doesn't run Mozart, so its fallback note looks like a silent fallback. What stands: the tooltip should follow who actually routed the message.

**1. What's wrong.** `routedHtml()` (`app.js` ~409–420) has two tooltips. Every note that isn't Mozart's gets
*"Mozart couldn't answer, so a simple rule chose…"*, including notes for deterministic routing such as
`→ Leo · reply to Leo's message` or an @mention, where Mozart was never asked. The reverse also happens: when Mozart
really failed or timed out (`fallback()` in `mozart.ts` ~124–134), the visible text is just
`→ Emily · nobody in the conversation`, which doesn't say Mozart failed (`docs/behaviour.md` says it should read
"(Mozart failed)").

**2. How to reproduce.** Stub, `#dark-mode`: hover the note under `B. And no flash of the light theme on load.`
(`→ Leo · reply to Leo's message`); the tooltip says Mozart couldn't answer. In a new channel send
`can someone check why the build is slow?`: the note reads `→ Emily · nobody in the conversation`.

**3. Expected.** Three distinct cases, each with matching text and tooltip:
- Direct: `→ Leo · reply to Leo's message` / `→ Leo · @mentioned`; tooltip "You addressed Leo directly."
- Mozart: as today.
- Fallback: `→ Emily · Mozart unavailable, Emily takes new topics`; tooltip names the rule used.
Pass the kind from the server (`routeWhy` prefix or a `routeKind` field) instead of guessing from the text.

**4. Why.** The note is how the user learns why someone answered. Wrong explanations erode trust in routing, and a
silent fallback hides that Mozart is failing, which the user would want to know.

**5. Inspiration.** Gmail's "Why is this message in Spam?" and Inbox's category explanations; GitHub's
"Review requested due to CODEOWNERS" vs "requested by @x".

## F12 · Medium · "Typing…" makes the sidebar and header jump

**1. What's wrong.** When a teammate starts typing, its channel row in the sidebar grows a second line
(`Emily is typing…`), pushing every row below it down; when it stops, they jump back. In the header, the folder line
is replaced by `Emily is typing…`, so the path vanishes for the length of the turn.

**2. How to reproduce.** Stub. Create a channel with no preview line yet (or use one whose row is one line), send a
message that names nobody, and watch the sidebar: the rows under it move down and back.

**3. Expected.** No layout shift: every channel row reserves its second line (empty or last-message preview), and
typing replaces the preview text in place. In the header, show typing in the composer's typing bar (already there,
with Stop) and leave the folder line alone, or swap in place on a fixed-height line.

**4. Why.** Moving targets cause misclicks, especially in a list you click all day, and it's distracting while
several teammates work.

**5. Inspiration.** WhatsApp (the preview line turns into "typing…" in place, the row never changes height); Slack
(typing shows under the composer only); Google's CLS guidance for layout stability.

## F13 · Low · New channel: prefilled folder may not exist; the name is changed silently

**1. What's wrong.** The New channel dialog prefills **Working folder** with the current channel's folder. If that
folder is gone (moved project, demo data), the first Create fails with *No such folder*. The **Name** is normalised
on create (`Audit Test Channel!` becomes `#audit-test-channel`) with no preview, so the user finds out afterwards.

**2. How to reproduce.** Stub with demo data (channels point at `~/Projects/notes-app`, which usually doesn't exist).
Click ✎ next to Search, type `Audit Test Channel!`, click Create: *No such folder*. Fix the folder and create: the
channel is `#audit-test-channel`.

**3. Expected.** Prefill the default working folder (or the current channel's only if it exists), and check the
folder on input with a quiet ✓ / "No such folder" next to the field. Under the name: "Will be created as
#audit-test-channel". Mark the field invalid (`aria-invalid`, `aria-describedby`) and keep focus on it when Create
fails.

**4. Why.** Errors you could have prevented feel like the app's fault; showing the final name avoids a rename later.

**5. Inspiration.** Slack's create-channel dialog (live "names must be lowercase…" and the resulting name as you
type); macOS open panels that only offer folders that exist.

## F14 · Low · Usage page columns don't line up between tables

**1. What's wrong.** Each card on the Usage page (By kind of run / teammate / model / channel / day) is its own table
sized to its content, so Runs, Cost, Input tokens and From cache sit at a different x in every card. Comparing
numbers down the page means re-finding the column each time.

**2. How to reproduce.** Stub, after a few messages. Click *What the runs cost ›*. Compare the x of "Cost" in By kind
of run, By teammate and By model.

**3. Expected.** One column template for all the tables (`table-layout: fixed` with shared widths, or one CSS grid
template), numbers right-aligned with `font-variant-numeric: tabular-nums`, so every figure in a column lines up
down the page.

**4. Why.** It's a comparison page: alignment is what makes it scannable.

**5. Inspiration.** Stripe's and Vercel's usage dashboards; Edward Tufte's and Apple's guidance on tabular numerals.

## F15 · Low · The plan meter's colour and its label disagree

**1. What's wrong.** At 80% weekly with the reset 2 h 27 m away, the weekly bar is amber (the "past 80%" rule) while
the line under it says `▼ under pace`. One says worry, the other says you're fine.

**2. How to reproduce.** In the stub, edit `probeUsage`'s stub numbers to `seven_day: { utilization: 0.8, resetsAt:

**5. Inspiration.** The `usage-limits-band` Claude Code mod it's modelled on; Apple's Screen Time and battery
"Low Power" messages, where colour and text always agree.

## F17 · Low · Archived channels look live in the sidebar

**1. What's wrong.** Expanding **Archived** lists archived channels (e.g. `search-spike`) in the same weight and colour
as live ones, right under the live list. They're read-only, so they should read as such.

**2. How to reproduce.** Stub: click **Archived** in the sidebar.

**3. Expected.** Muted text (`--muted-foreground`), an archive icon instead of `#`, and no unread badges; the
channel's own header already says it's archived.

**4. Why.** It prevents opening a read-only channel to post in it, and keeps the live list visually separate.

**5. Inspiration.** Slack's archived channels (greyed with an archive icon); Linear's archived projects.

## F18 · Low · `aria-live` on the whole message list

**1. What's wrong.** `#messages` has `aria-live="polite"` (`index.html` line 125). Switching channels replaces the
whole list, so a screen reader announces the entire channel; every re-render of a job card re-announces it.

**2. How to reproduce.** VoiceOver on (⌘F5), switch channels: it starts reading the whole history.

**3. Expected.** `role="log"` on the list with `aria-live` only reaching new messages (or a separate visually hidden
live region that gets "Elliot: Done. The toggle is in Settings…" for each new message). No announcement on channel
switch beyond the channel name.

**4. Why.** Live regions should announce changes, not content the user navigated to.

**5. Inspiration.** WAI-ARIA `log` role (APG chat example); Slack's screen-reader mode, which announces new messages
only.

## F19 · Low · The job card shows above the message that announces it

**1. What's wrong.** When a teammate starts a job during a turn, the job card is posted first (when `start_job`
runs) and the teammate's reply (`On it, I started a job.`) is posted after it, so you read the card before the
message that explains it. Seen in the stub and in real channels.

**2. How to reproduce.** Stub: `@Elliot start a job stub-permission`. Order: Elliot's `j2` card, then
`(stub) On it, I started a job.`

**3. Expected.** Within one teammate turn, the text comes first and the cards it created go under it (render-time
grouping by turn is enough; no change to what's stored).

**4. Why.** Reading order should match cause and effect: the message, then the work it kicked off.

**5. Inspiration.** Slack apps post the message with its attachment card underneath; GitHub comments show the text,
then the linked checks.
